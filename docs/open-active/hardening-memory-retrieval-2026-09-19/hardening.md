# Security Hardening Review: 有界历史工具结果检索

## Evidence Basis

我们从 [证据清单](context.md) 的请求容量记录和当前源码出发。账本已经保存部分工具结果的脱敏内容，但没有面向模型的历史搜索、按引用读取和统一请求预算。现有脱敏是模式匹配，不能证明任意测试日志或 MCP 输出不含敏感内容。这是设计评估，不是安全扫描或已修复声明。

## Constraints

用户确定：先支持测试和 MCP 等难以重现的结果；文件历史正文快照不进入首版。MCP 至少限于白名单内的服务及工具。**敏感日志不得进入模型服务，首次工具回执和历史检索均受此约束。**测试正文是否可读尚未决定。用户希望完成长任务，同时控制上下文失真与成本。没有给定可接受的额外磁盘占用或延迟；这些数值必须实测。并行源码修改使实现前必须重新核对接线。当前 Docker runner 将整个仓库只读挂载进容器（E5），所以它不能单独作为“合成数据测试”的证明。

## Recommendation Summary

我建议用已有账本提供调用身份和状态，但不要把旧 `result.content` 直接视为模型可检索正文。旧记录先建安全元数据索引；新回合在统一的**模型入口**形成安全投影，并将同一投影用于首次工具回执和持久化后的历史读取。安全投影含来源、结果状态、版本、截断说明和允许的诊断字段；未知内容只给元数据。读取入口还需检查线程、工作区、调用者权限及完整请求容量。模式脱敏只能作为辅助。原始日志的更长本地留存是后续独立议题。

## Next Decisions

MCP 检索候选先要求服务、工具及绑定身份仍在白名单内；返回正文还须通过模型入口的数据策略。测试 profile 是固定命令身份，不能证明 stdout/stderr 安全。单靠 profile、状态和退出码常不足以修复问题。建议将诊断分为两类：**运行时已切断敏感数据可达性**的测试可以向模型提供有界的详细失败信息；其余测试仅提供固定结构化诊断，并允许模型通过有界、定向的安全重测逐步缩小原因。安全测试需要一个只含允许文件和合成输入的独立工作区、无凭证的环境与镜像、禁用网络，并核实实际运行配置；读取整仓库的 Docker 测试不能自动归入此类。原始敏感日志不得直接作为首次工具回执、压缩摘要输入或历史检索正文进入模型。能否建立这种安全复现环境、日志本地保留期限，仍待商讨。内容级外发控制需单独设计；历史检索不能给上传工具授予新权限。

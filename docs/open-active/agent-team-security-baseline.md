# 产品级 Agent Team 安全基线,与本仓库的差距

日期:2026-11-02。基线提交:`01d8305`。

这份文档做三件事:把产品级多 Agent 系统的安全做法整理成基线;逐维度对照本仓库;按差距列出安全问题。

**一句话结论**:产品级系统的共识是——**工具白名单是"引导",不是安全边界;真正的边界是沙箱 + 逐跳可验证的身份链**。本仓库前半段(沙箱、账本、预算、深度)已经对齐,后半段(委派链身份)是空的,而且实测确认可以被伪造。

## 1. 基线:产品级怎么做

| # | 原则 | 具体做法 | 来源 |
| --- | --- | --- | --- |
| B1 | **安全边界放在操作系统,不放在工具列表** | 官方文档明确写:工具限制是"steering",不是安全边界;只读代理只要带 Bash 就不是只读的 | Claude Code 子代理文档 |
| B2 | **权限模式继承不能被下级收窄** | 父会话用 `bypassPermissions` 时,所有子代理继承且无法下调——这是已知提权面 | Claude Code 文档 + issue #20264 |
| B3 | **deny 优先,跨层合并** | `deny → ask → allow`,任一层 deny 即阻断;hook 在权限模式判定之前触发 | Claude Code 权限模型 |
| B4 | **委派链身份逐跳存活** | 用 RFC 8693 的 `sub`(原始主体)+ 嵌套 `act`(当前执行者);"重新自签"= 制造混淆代理 | DataRobot 分析 / RFC 8693 |
| B5 | **单调收窄 + 有界深度** | 子代理的 scope / 预算 / 有效期只能是父级子集,只减不增;委派深度默认 3 | IETF AIP 草案 / A2A 信任草案 |
| B6 | **自证根是最弱环节** | "一条委派链的强度取决于链上最弱的身份声明";自证根会让下游全部失效 | A2A 社区工作组 |
| B7 | **互信即漏洞** | AutoGen / MetaGPT 被实证:低权代理通过自然语言诱导高权 supervisor 代其执行敏感工具(confused deputy);子代理还能"冒名"操纵 supervisor 拿更大任务(show-up attack) | 相关论文与 COSAI 风险条目 |
| B8 | **凭证不继承** | 子代理默认不继承父的 OAuth/token;应发短期、绑定自身、按调用授权的凭证 | Permit.io / 多份实现指南 |
| B9 | **两级身份审计** | 每条动作同时记录"发起者"和"代理者";检测条件为 `deputy.allowed=true 且 initiator.allowed=false` | SAF-T1307 |

## 3. 安全发现

### F1(P0,实测)身份名字由调用方指定,而授权按名字匹配

**攻击路径**:
1. 一个 principal 为 `worker` 的父代理,scope 含 `workspace.write`。
2. 它 spawn 子代理时传 `principal_id="root"`。
3. scope 校验通过(确实是子集)。
4. 子代理被记成 `root`;策略规则里 `principal_ids=("root",)` 直接命中。

**实测输出**(探针 `scripts/probe_delegation_identity.py`):

```
parent principal: worker scopes: ('workspace.read', 'workspace.write')
PART A : ACCEPTED -> child principal: root
PART A2: refused -> child_scope_escalation
PART B : narrowed principal_id= root parent= worker scopes=('workspace.write',)
PART B2: rule principal_ids=('root',) | name matches: True
```

**影响**:scope 收窄挡不住这条,因为父级本来就有那些 scope。漏洞在"名字即权限"。

**现有兜底**:无。

**对齐的基线**:B4 / B6 —— 身份不可自签。

### F2(P0,代码推断)根代理创建没有授权来源

`_spawn_root`(`agents/control.py:351` 起)只做幂等,`principal_id` 和 `scopes` 全部直接取自调用方。

**影响**:自证根。即使子代理身份链修好了,根节点仍然是谁调用谁说了算。

**对齐的基线**:B6。

### F3(P1,代码推断)邮箱发送方可以伪造

`send_message(..., from_agent_id=...)`(`control.py:1026`)接受调用方指定的发送者,不校验调用者身份,也不校验发送者与接收者的关系。

**影响**:任意持有控制面对象的代码可以冒充上级给任意代理发指令。接真模型后,如果子代理能触达控制面,这就是"冒名下发任务"。

**对齐的基线**:B4 / B7(show-up attack 的机制之一就是伪造来源)。

### F4(P1,代码推断)邮箱没有信任等级

消息体只有 `body_ref`,没有"这段内容来自不可信输入"的标记。T7 文档已声明:`子可能把含不可信内容的父消息当可信指令`。

**影响**:父代理转述的仓库文本,子代理会当任务指令执行。

**对齐的基线**:B7。

### F5(P1,代码推断)历史日志不能自证

scope 包含关系只在**写入时**校验(`_validate_spawn_parent`)。回放/重建时不再重验:日志里如果存在一条越权 spawn,重放会照样接受。

**影响**:本仓库其他地方坚持"缓存必须复算验证",但委派这一层没有。日志被篡改或曾经有 bug 时,历史无法自证。

**对齐的基线**:B4(可验证的授权链)。

### F6(P2,有产品级证据)工具白名单被当成边界

Claude Code 文档明说工具限制是 steering;只读代理只要带 Bash 就不是只读。本仓库的 shell 设计已经意识到这点(所以不接受 shell 字符串),但文档里仍有"白名单=防护"的表述残留。

**影响**:不是代码漏洞,是**认知风险**——会让人把"没进白名单"当成"做不到",从而不敢开容器。

**对齐的基线**:B1。

### F7(P2,代码推断)没有"授权凭据"字段

`agent.spawned.v2` 记录了父子关系和 scopes,但没有记录"哪一次父级授权允许了这次 spawn"的摘要/签名。

**影响**:事后无法证明子代理的权限确实来自父级授权,只能相信写入时的校验。

**对齐的基线**:B9(两级身份审计)。

## 4. 优先级

1. **P0,接真模型前必须**:F1、F2。最小闭环是——spawn 必须走 `Principal.narrow()`,principal 名字全局唯一或改成不可猜测 id,根代理创建要有明确授权来源,并加一条"父代理起名 root 必须被拒"的反例测试。
2. **P1**:F3、F4、F5。邮箱发送方校验 + 消息信任标记 + 回放重验。
3. **P2**:F6(改文档表述)、F7(事件加授权摘要)。

## 6. 诚实边界

## 7. F1 的修复方向:签名 token + 续约(待定,此处只记录设计)

### 7.1 先纠正一点:光加 token 不够

token 解决的是"身份能不能被伪造",不解决"谁有权签发"。**F2 不修的话,签名只是把"随便起名"换成"随便签"**——自签的 token 和自填的名字一样不可信。所以两件事要一起做,或者至少先做第一步(见 7.7)。

### 7.2 token 应该长什么样

| 字段 | 作用 |
| --- | --- |
| `issuer` | 签发者的 `agent_id`(不是名字) |
| `subject` | **子代理的 `agent_id`(UUID)**,不是 principal 名字 |
| `scopes` | 收窄后的集合,续约时不得扩大 |
| `run_id` / `attempt` | 绑定当前运行;旧 run 的 token 自动失效 |
| `not_before` / `expires_at` | 用数据库时钟,不用本地墙钟 |
| `absolute_expires_at` | 任务总上限,续约不能越过 |
| `parent_token_digest` | 链式绑定,让"授权来自哪一次父级授权"可验证 |
| `signature` | 运行时密钥签名或 MAC |

**不落库明文。** 事件里只存 digest——仓库的既有纪律是"凭据字段不进事件、不进日志",委派 token 属于凭据。

### 7.3 验证点放在每次动作,不是每次 spawn

在动作解析 / 账本 claim 之前验证。过期、撤销、run 变更、scope 越界一律拒绝。

**不允许过期后回落到名字匹配**——那等于把 F1 又放回来。

### 7.4 过期与长任务:三个选项

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 全程长 token | TTL = 任务上限 | 实现最简单 | 泄漏窗口等于任务时长;跑 2 小时就给 2 小时权限 |
| B 短 TTL 纯自动续 | 子代理自己续 | 也简单 | 等于永不失效,安全性形同虚设 |
| C 短 TTL + 上级确认续约 | 子代理申请,leader 确认后重签 | 权限窗口小;leader 可随时撤 | leader 挂了子代理停摆;要防"无限续" |

**推荐 C + 硬上限**:单次 TTL 与 lease 对齐(短),续约由 leader 用自己的 token 签"同一任务、同一 scope、仍归我",并且 token 带 `absolute_expires_at`,续约次数与频率都记账。这样"任务可能很长"不会变成"权限可能很久"。

如果某个任务确实超过总上限,正确的做法是**分阶段**:每个阶段重新走一次授权,而不是给一个超长 token。

### 7.5 续约可以直接复用现有心跳

仓库已经有 `AgentLeaseKeeper`(lease 3–3600 秒,心跳间隔 = lease/3)和 `agent.heartbeat.v2` 事件;心跳已经绑定 `(agent_id, run_id, attempt)`,run 或 attempt 一变就 `agent_lease_lost`。

所以续约不需要新协议:

1. 子代理心跳时,顺带检查 token 余量;
2. 余量不足 → 向上级申请续约;
3. 上级用自己的 token 签名确认(同一任务、同一 scope、未撤销);
4. 重签:只延长 `expires_at`,`absolute_expires_at` 不变。

**跨 token 的生命周期天然与 lease 对齐**,不需要额外的心跳协议。

### 7.6 边界情况

| 情况 | 处理 |
| --- | --- |
| leader 挂了 | 不等待续约,走既有 orphan takeover;新 attempt 签发新 token,旧 token 因 run 变更失效 |
| 子代理自己给自己续 | 不允许。续约必须由上级签发,否则等于无限期 |
| 续约时想扩权 | 拒绝。续约只能延长,不能加 scope |
| 频繁续约 | 计入预算,防刷 |
| 时钟偏差 | 统一用 `database_time`,不用本地时钟 |
| 撤销 | 在 root 上记 revocation epoch,验证时比对;撤销后即使 token 未过期也拒绝 |
| token 泄漏 | 因为绑定 run/attempt 且有 absolute 上限,影响窗口有界 |

### 7.7 落地顺序(重要)

1. **先让身份不可伪造**:`subject` 从名字改成 `agent_id`,策略规则按 id 绑定而不是按名字字符串。**这一步单独就能消灭 F1**,而且不依赖签名体系。
2. **再加 TTL 与每动作验证**:此时 token 可以是运行时内部结构,不一定要真实签名。
3. **最后加续约 + 硬上限 + 撤销**:配合 F2 的可信根,才谈得上"签名"。

反过来做(先上签名)会得到一个自签的 token——比名字好一点,但根上还是自证。

# 任务工作区模式决策记录

更新于 2026-11-21。`read_only` 的设计已定稿，`sandbox_write` 和 `workspace_write` 正在逐项确认。第四档命名为 `user_trust`，已记录其挂载与工具授权规则。关联讨论见 [Agent Team 环境与信任边界 #18](https://github.com/Koawa265Richard31/Koawa.codingAgentV2/issues/18) 和 [子 Agent 多轮执行 #36](https://github.com/Koawa265Richard31/Koawa.codingAgentV2/issues/36)。

## `read_only` 已定稿

| 项目 | 约定 |
| --- | --- |
| 用户入口 | 用户选择一个文件夹。该目录是授权范围的上限，即使 Git 工作树的根在其上级也一样。宿主 Runtime 直接读本地文件，无需沙箱或 `git init`。 |
| 识别入口 | Runtime 分别寻找业务代码和测试入口，支持多模块。只找到一类时，从同级和项目根继续补找另一类，例如同时识别根目录的 `app.py` 和 `tests/`。两类都未命中时，从整个所选目录识别可读文件，包含根目录文件。 |
| 路径边界 | 初始入口外的文件或目录可按下节申请扩围。生成可读路径清单和每次打开文件时，均按实际解析后的路径校验授权范围及排除项。 |
| 模型工具 | 模型拿到可读路径，只能调用内置 `read_file`。MCP 服务不启动、不连接。业务和测试代码均按文本读取，任务不运行 Shell、项目代码或测试，也不访问数据库。 |
| Git 状态 | 已有 Git 工作树时，由 Runtime 在每次用户提问开始时采集带时间的状态摘要，只列可读范围内的变化。查询使用固定的只读参数，避免可选的索引写回。普通文件夹直接阅读，若查询失败则标记“Git 状态未知”，继续任务。 |

验收时可选一个根目录带 `app.py`、子目录带 `tests/` 的普通文件夹。两处代码均应可读，环境和数据库文件应被拒绝，目录中不产生 `.git`。另用已有 Git 工作树验证只返回可读范围内的状态。

现有装配会创建 `GitFacade`，常规只读工具分组还含 `git_diff` 和 `update_plan`。实现本模式时，需要单独装配文件读取和可选的 Git 状态查询。[Runtime 装配](../../src/koawa_agent_v2/runtime/assembly.py) · [Git 状态采集](../../src/koawa_agent_v2/verification/git.py)

## 两种模式共用的读取范围与扩围审批

`read_only` 和 `sandbox_write` 使用同一套文件夹选择、业务与测试入口识别及兜底规则。用户选中的文件夹是可以申请访问的上限。实际可读范围由初始入口和已获批的新增路径组成，并始终扣除排除项。

| 请求的目标 | Runtime 行为 |
| --- | --- |
| 已在有效可读范围内 | `read_only` 可用 `read_file` 读取。`sandbox_write` 只将本次获准读取的文件或目录作为沙箱输入。 |
| 在选定工作区内、位于有效可读范围外，且未命中排除项 | 可就具体文件或目录申请读取权限。Runtime 返回待审批请求，含申请路径、目标类型和用途。审批通过后才更新范围并允许读取，或将该路径以只读输入提供给沙箱。拒绝后保留原范围。 |
| 工作区之外，或属于数据库文件和目录、环境文件、虚拟环境、Git 元数据 | 直接拒绝，不进入扩围审批。批准父目录时，其内部命中排除规则的文件和子目录也须剔除。 |

例如，初始入口是 `src/` 和 `tests/`，任务需要 `docs/billing.md`。在批准前，模型不能取得该文件正文，沙箱内也看不到它。批准这个文件后，同级文件仍按各自的授权处理。申请由 Runtime 的审批流程承载，`read_only` 的模型工具仍只有 `read_file`。

## `sandbox_write` 讨论中

### 已确认的工作区与交付规则

1. 根 Agent 在断网沙箱内的独立 Git worktree 编辑。普通文件夹也能进入本模式。Runtime 只导入获准读取的当前文件，在沙箱私有副本中初始化 Git，并用编辑前的文件建立基线提交。宿主普通目录不执行 `git init`。交付时按文件快照核对目标，最终只写回用户批准的改动。已有 Git 仓库的起始快照同样包含授权范围内已有的未提交修改。
2. 初始挂载和后续扩围都以有效可读范围为准。目录中有排除项时，先形成过滤后的只读输入，再供沙箱使用。单文件审批只增加该文件。扩围保留 worktree 里已有的编辑，新增只读输入不计入 Agent 的变更，也不自动取得写入或交付权限。宿主 `.git` 仍受排除规则约束，沙箱使用自己的 Git 元数据。
3. 模型后续读取、打补丁和测试针对同一份候选代码。父级派单时指定任务、路径、工具和起点。起点可以是指定提交，也可以是含父级未提交改动的快照。子 Agent 的范围只能在父级实际权限内，缺少必要路径或请求越权时，Runtime 向父级报告。
4. 父级只采纳最终补丁通过规定测试的子任务。父级将自己的修改和已采纳的子补丁组合起来，对最终版本跑完相应测试集合，随后向用户返回实际要写进宿主工作区的完整 diff。**用户批准这份 diff 后，Runtime 才能写回。** 等待或拒绝审批期间，宿主不接收补丁。写入前复核目标工作区、基线和补丁版本。补丁变更后重新测试并提交新版本供用户审批。

### 交付审批的结构化返回

本轮确定 Runtime 必须给调用方返回可展示的完整 diff 和待审批状态。CLI 面板可以后做。下表是建议的数据字段，可沿用 `CommandOutcome.payload` 及现有审批记录的标识、版本和状态。调用方可以先通过结构化接口取得 diff，并针对同一版本提交用户决定。[命令返回与审批入口](../../src/koawa_agent_v2/runtime/app.py)

| 建议字段 | 类型与用途 |
| --- | --- |
| `kind`、`request_id`、`version`、`status` | 建议交付类型为 `workspace_delivery`，同时返回审批请求 UUID、版本整数与审批状态。初次状态为 `pending`。 |
| `workspace_ref`、`base_snapshot_ref` | 标识目标工作区和本次比对的基线快照。 |
| `diff`、`patch_digest` | `diff` 是供用户审阅的完整差异文本，`patch_digest` 标识实际待应用的那份补丁。 |
| `integration_receipt_ref` | 指向最终候选通过规定测试的集成回执。 |

可用一个普通文件夹验收交付流程。在沙箱内修改一个文件并让测试通过。调用方应先拿到待审批请求和 diff，此时宿主文件保持原内容。拒绝时同样保持原内容。批准 A 版后若候选已成为 B 版，A 版批准不能用于 B 版写入。

### 沙箱网络与工具

`sandbox_write` 的整个任务容器断网，包括测试及其子进程。本模式禁用 MCP，Runtime 不启动或连接 MCP 服务，也不提供宿主 MCP 代调用。任务专用虚拟数据库的数据来源、虚拟环境（`venv`）及可传入的环境配置仍待逐项确认。

### 当前实现对照

常规补丁工具绑定 `config.repo`。`WorktreeManager.create()` 目前在宿主执行 `git worktree add`，遇到有未提交修改的用户工作区会拒绝创建写任务的 worktree。Docker 测试 runner 以只读方式挂载 `/workspace`。`DurableArtifactIntegrator.deliver()` 会校验测试回执，并在目标仓库的 `.git` 下加锁。普通宿主文件夹的交付需要支持基于文件快照的校验和独立于宿主 `.git` 的交付锁。[Runtime 装配](../../src/koawa_agent_v2/runtime/assembly.py) · [工作树管理](../../src/koawa_agent_v2/workspace/worktree.py) · [Docker 测试挂载](../../src/koawa_agent_v2/sandbox/runtime.py) · [集成与交付](../../src/koawa_agent_v2/workspace/integration.py)

## `workspace_write` 讨论中

本模式允许将任务产生的补丁写回宿主原目录中已授予写权限的业务和测试路径。保留独立 Git worktree，以支持根 Agent 和多个写子 Agent 并行工作。任务可按网络白名单联网、使用获准的 MCP。测试继续在沙箱中执行，可从宿主提供测试所需的环境配置。

### 已确认的工作区与免审批写回规则

1. 根 Agent 在自己的 worktree 保留候选代码，每个承担写任务的子 Agent 使用独立 worktree，基线由父级指定。生成当前工作区快照时纳入获准范围内已有的未提交改动。父级决定采纳哪些已经通过规定测试的最终子补丁，再对集成后的最终版本运行规定的测试集合。
2. 从获准的候选 worktree 写回时，Runtime 核对整个补丁的实际目标路径、目标基线和已测版本。所有变更都在预先授予的写入范围内且校验通过，就可以应用到宿主原目录，无需再向用户请求逐补丁或最终 diff 审批。目标基线不再匹配或补丁含越界路径时，整份补丁停止应用。仅获准读取或挂载的路径不因此获得写权限。
3. 实现时建议返回已应用的 diff 和测试回执，供用户查看、追溯。此前为 `sandbox_write` 确定的用户交付审批仍适用于该模式。选择 `workspace_write` 意味着已授权路径内的修改可能在用户逐行查看之前进入宿主目录。

验收时可授权写入 `src/`，同时只授予 `docs/` 的读取权限。仅修改 `src/` 的最终补丁应在集成测试和基线校验通过后直接写回。若同一补丁还修改了 `docs/`，两处改动均不写回。

### 测试环境、MCP 与网络

- 测试配置可以由宿主提供。建议在测试配置中声明所需变量及依赖，例如测试库的连接配置。工作区可用的数据库、账号和读写权限按任务授予。
- 网络出口只允许白名单中的目的地，MCP 可用工具按任务授予。MCP 涉及项目文件写入时，也须遵守相同的路径、候选与写回规则。将需要联网的 MCP 服务放在独立容器是待评估方案。现有 MCP 容器使用 `--network none`，允许指定目的地需要相应的出口控制。[MCP 容器参数](../../src/koawa_agent_v2/sandbox/docker_primitives.py) · [MCP 工具配置](../../src/koawa_agent_v2/runtime/config.py)
- 哪些测试需要联网由具体测试配置决定。建议测试默认断网，有需要时单独指定允许的目标。

## `user_trust` 挂载与工具授权

用户显式选择此模式并挂载目录。挂载动作授予该目录树内全部文件的读写权限，仍受宿主操作系统权限限制。这里按实际挂载的目录划定范围，入口识别及低权限模式的文件排除清单不适用于此档。挂载目录内实际存在的环境文件、数据库文件和 Git 元数据也在授权范围内。

| 请求 | 规则 |
| --- | --- |
| 读写挂载范围内的文件 | 自动获得路径授权，无需再逐文件申请。按实际文件位置核对边界。 |
| 读取挂载范围外的文件 | 用户要求扩展读取时，先返回待审批的具体目标。批准之前不读取正文。批准只增加指定目标的读取权限，未批准的其他路径和目录外写入不在此次授权内。 |
| 使用 MCP 或其他工具 | 用户实际装配的所有 MCP 和工具均可调用。仓库内容或模型提议的新工具不能自行取得“用户已装配”的身份。测试可按此前设计分为沙箱和宿主运行，出网目的地按白名单控制。 |

### 已确认的工具文件访问边界

**工具可信、可以启动，并不自动扩大本次任务的挂载范围。** 内置工具、MCP、Shell、宿主测试及其子进程只能通过受限文件接口或操作系统级边界访问获准路径。

由 Runtime 代读时，在实际打开文件之前核对解析后的路径和操作类型。能自行打开文件的进程须由操作系统限制其文件访问范围。仅检查工具启动参数无法约束进程后续打开的文件。若现有执行方式不能落实该边界，应返回原因，避免以宿主完整权限运行。

验收时挂载 `project/`，分别通过 `read_file` 和已装配的本地 MCP 请求读取同级 `shared/schema.json`。审批前两条路径都不能取得正文。批准本任务读取该文件后，两者可在各自已有工具权限内读取它。写入该文件以及读取 `shared/` 内其他文件仍未获授权。

### 与现有实现的区别

旧 `host_trust=user_confirmed` 是宿主测试信任设置，当前分支的配置解析可默认取这个值。启用新模式需要用户显式选择，旧配置不能自动转换成整个挂载目录的读写授权。现有 `read_file` 还会拒绝 Git 控制路径，MCP 装配支持宿主和沙箱两种执行环境。以上规则记录的是目标行为。[旧信任配置](../../src/koawa_agent_v2/runtime/config.py) · [当前文件读取](../../src/koawa_agent_v2/tools/repository.py) · [MCP 装配](../../src/koawa_agent_v2/runtime/assembly.py)

## 块序列（4 块 + 收尾）

**Block 0 定位**：R1 守 ①→②，R2 守 ②→③，**R3 守 ②的内容本身**。
病历三处：①recall 直接返回 user_input/final_text 前 120 字（L90-92）；
②verification 回执删了 stdout/stderr 但仍返回 argv/exit_code/duration；
③MCP 返回正文长度。共同病根 = 按统一字段直接公开，无法表达按接收方的
释放权限。

**Block 1 recall 的病与治**：裁短为什么不是安全措施（截断只缩小泄漏量，
不改变泄漏性质——历史输入可能含秘密，120 字照样带得走）；治法 = 删预览、
留长度元数据、新增 `content_release: "unavailable_without_release_rule"`
独立状态（缺规则 = 显式不可提供，不冒充错误、不回退原文）。
检查点：为什么"缺释放规则"要造**新状态**，而不是复用"失败"或返回空？
（提示：Block 1 的 untrusted/unverified 之分在这里第三次重演——语义分类
保护消费通道）

**Block 2 表达力缺口 vs 隐藏命令**：裁决原话"在获准的安全测试中返回这些
诊断是合理能力；问题是当前实现……不能表达敏感测试的不同释放权限。**不是
要求一律隐藏所有结果**"。argv/exit_code 没修为什么是**对的**：释放规则
是部署输入（维护者定义），设计约束禁止由实现推导授权——工程可以执行
策略，不能发明策略。检查点：这格没修反而该加分——用一句话说清
"工程不做授权决定"的边界在哪边。

**Block 3 结论限定的诚实**：`test_hit_text_never_reaches_provider_request`
观察的是请求上下文项（.content），**非完整 provider 协议序列化**——复验
第三轮要求把结论从"wire 级不泄漏"降级为"历史预览不再经该检索回执泄漏"。
检查点：为什么要降级？（证据层规则 v1.1 再应用：观察到哪层就只能声称
哪层——测了 .content 就没有资格声称 wire 级）

**Block 4 三态残余**：withheld（保留待批）/ human_required（需要人批）/
可披露 的独立语义未完整落地。检查点：为什么"不可披露"不能伪装成"测试
失败"？（失败会触发补丁/重测——探测式重测恰恰把秘密又撞了一遍；独立
状态 = 不给下游任何重试的借口）

## 焊线追踪（单对象法，R2 的成功配方）

追踪一个值：`user_input` 的前 120 字。
- 修复前的一生：recall 命中 → 切片 [:120] → 进回执 → 进上下文 → 进 provider
  请求（泄漏路径全程绿）
- 修复后的一生：存储里躺着 → recall 只吐 `user_input_chars: 247` →
  `content_release: "unavailable_without_release_rule"` → 文本从未离开存储

  规则——而这正是那格没修的部分，你能看见门在哪，也知道为什么门暂时锁着）
